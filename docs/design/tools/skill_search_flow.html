skill_search · 接口设计与取舍

harness 框架原本把全部技能描述塞进 system prompt，让主模型「看着办」——token 随技能数线性增长，且判断不可校准。skill_search 把「选哪个技能」变成一次独立的决策调用：输入查询与候选花名册，输出每个技能的校准概率与建议，是否加载由调用方决定。

1 · 输入
querystring必填
用户查询原文，不改写、不摘要
skillsarray必填
候选花名册 [{name, description}]
threshold…9 个参数可选
全部有默认值，响应回显实际使用值
2 · 组装（服务端完成，调用方无感）
一次调用就是下面这份 JSON：一份共享 state（这次要判断什么）+ 一组 questions（这里只有 1 道单选题）。字符串有节选，// 为注解。
{
  "state": {                  // 共享上下文：只描述任务，不含花名册
    "task": "判断哪个候选技能最适合查询，或是否不需要任何技能",
    "context": "用户发送了一条查询。助手有一份候选技能列表，每个技能
            有名称和描述。技能是完成某类特定任务的指导说明、流程规范
            或最佳实践——不是仅仅与查询共享关键词的工具或 API。
            加载技能意味着遵循其文档化的流程来处理请求。",
    "query": "帮我做一份介绍公司 Q3 业绩的 PPT"   // ← 输入的 query 原样放这
  },
  "questions": {              // 问题集：一次调用可带多题，这里 1 道单选
    "pick": {
      "type": "choice",
      "instructions": "选出真正需要加载并遵循其指导的那个选项。只有
                流程直接对应请求才选，共享关键词不算…",
      "criteria": {             // 选项 = 花名册内联 + 逃生舱
        "s0": "ppt-architect: Create presentation slide decks…",
        "s1": "html-ppt: Author professional HTML presentations…",
        "s2": "pdf: Read, extract, merge and split PDF files.",

      }
    }
  }
}

为什么这么设计

三个关键取舍，每个都有真实 API 的 A/B 实验支撑（6 个测试场景：1 个明确命中、1 个纯文字可答、4 个「花名册故意缺了对应技能」的盲区场景）。

Q1怎么判断「这个请求根本不需要任何技能」？
单选题必然产生一个赢家，但概率最高 ≠ 正确——如果花名册里其实没有合适的技能，模型也会硬选一个。必须给模型一个说出「都不合适」的出口。问题是：这个出口放在哪？
✗ 方案 A：先做一道独立的是非题 先单独问「这个查询需要技能吗？」，回答「需要」再进入单选。但这道是非题只看 query、看不到花名册。例：用户说「检查 MCP 服务质量」，花名册里只有「构建 MCP 服务」的技能——是非题回答「需要技能」（没错），于是流程继续，最终错选「构建」技能。 实验：4 个盲区场景误判 3 个
✓ 方案 B：把「不需要技能」做成单选题的一个选项 __no_skill_needed__ 与所有技能同场竞技，能同时看到 query 和全部技能描述，于是分得清两种情况：纯文字就能答（不需要技能），以及「需要技能、但花名册里没有」（覆盖盲区）。 实验：6/6 全部正确，盲区场景 no_skill 概率 0.63–1.00
Q2怎么防止模型因为「关键词沾边」就乱选？
「检查 MCP 服务」和「构建 MCP 服务」共享大量关键词。如果提问方式不约束判断标准，模型会按话题相关性作答，把「同领域」当成「能解决」。
✗ 方案 A：问「这个技能与查询相关吗」 「相关」是模糊标准——共享关键词、属于同一领域都算相关。模型看到「MCP」「检查」就选了「构建 MCP 服务」的技能。 实验：旧措辞 6 场景只对 2 个
✓ 方案 B：把判断标准写进问题里 问题改为「遵循这个技能的文档化流程，是否会实质性改变这个请求的处理方式」——共享关键词不算数，流程必须直接对应请求的具体任务。 实验：新措辞 6/6，3 个盲区场景直接翻转
Q3技能描述放在请求的哪个位置？
一次调用由「共享上下文 state + 问题集」组成。全部技能描述既可以塞进 state，也可以写进每个选项的定义里——两种放法模型都能看到全部技能，差别在哪？
✗ 方案 A：全量塞进 state state 是「任务描述」的位置，塞进整个花名册会带入 triggers、路径、版本等与判断无关的字段，token 更贵，还稀释判断焦点。 实验：判断质量与方案 B 持平，但 token 成本更高
✓ 方案 B：内联为每个选项的定义 state 只留 task / context / query。单选题的归一化分布本来就要求模型同时比较全部选项，全局感知没有任何损失，token 却更省。 实验：质量持平、成本更低 → 采用

输入注意事项

  • description 超过 500 字符会被截断，且该技能永不自动 select，只进 review——截断意味着信息不全，不做自动裁决
  • skills ＞ 50 时自动走两步（先逐技能独立打分召回 top-5，再单选精排），对调用方无感
  • 模型答案缺失或畸形的技能标 invalid_response，只影响该项，绝不伪装成 select 或 skip
  • 阈值拿不准就用默认值，再按响应里回显的 thresholds 与 usage 逐步调校
